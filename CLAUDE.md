# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Engine Development Rule (non-negotiable)

Each of the 22 Core Engines must go through its FULL lifecycle (TASK-000 through TASK-006 LOCK) before work begins on the next Engine. No parallel Engine work. No starting a new Engine's TASK-001 while a previous Engine is still in progress. This was proven with Authentication Engine (fully migrated, tested, documented, and LOCKED before any other Engine was touched) and must be repeated for every subsequent Engine, in this exact order, unless explicitly told otherwise by the project owner.

Before starting any Engine that depends on another Engine's data (e.g. Booking Engine depends on Contract Engine for pricing), an **Interface Contract** document must exist first, defining exactly what functions/data one Engine provides to the other. Interface Contracts live in `docs/interface-contracts/`, named `<engine-a>-<engine-b>.md` (e.g. `contract-hotel-booking.md` for the Contract → Hotel → Booking data flow). This directory doesn't exist yet — create it when the first cross-Engine dependency actually needs one, rather than speculatively.

## Project

DMC Travel OS — a Destination Management System (DMC/tour-operator ERP: agents, hotels, contracts, rates, bookings, payments, finance, AI automation). Currently in early MVP stage: only authentication and agent-registration/approval are implemented end-to-end; most business modules listed in the design docs (hotels, contracts, rates, bookings, finance, transfers, charter, AI) do not exist in code yet.

## Governing documents — read before changing business logic

The numbered root-level docs are the project's spec and are treated as the source of truth for business rules, not just background reading:

- `00_MASTER_RULES.md` — golden rules. Notably: never change business logic without owner confirmation, don't remove existing features without reason, AI must follow `02_Logic_Rules.md` / `03_Domain_Model.md` / `04_Data_Dictionary` and must not invent its own business rules.
- `01_Modules_List.md` — full business module catalog (most are unbuilt).
- `02_Logic_Rules.md` — detailed workflow/status rules (agent registration, contracts, rates, bookings, etc.).
- `03_Domain_Model.md` — canonical entity/field definitions.
- `04_Data_Dictionary` (no extension, it's a text file, not a folder) — DB field dictionary. Note it specifies UUID primary keys + `tenant_id` on every table; actual code currently uses integer PKs and no multi-tenancy (see Reality vs. docs below).
- `05_Architecture.md` — target architecture (Postgres, Redis, Celery, S3, multi-tenant). Aspirational; current implementation is much simpler (see below).
- `06_API_Rules.md`, `07_UI_UX_Rules.md`, `08_Coding_Standards.md` — API/UI/coding conventions to follow for new work.
- `09_Project_Roadmap.md` — phase plan (currently in Phase 2 / MVP).
- `11_Decisions.md`, `12_REVIEW.md` — decision and review logs; templates are mostly still empty.

**Reality vs. docs gap:** the docs describe the long-term target (PostgreSQL, UUIDs, multi-tenant, Celery/Redis, S3). The actual backend today is a single-tenant FastAPI app on SQLite with integer auto-increment PKs and no queue/cache/storage layer. When implementing new features, follow the doc's business rules and API/module shape, but don't assume the infra described in `05_Architecture.md` already exists — check the code first.

## Commands

Backend (FastAPI, from `backend/`, using the committed `.venv`):
```
./.venv/Scripts/python.exe -m uvicorn main:app --reload --port 8001   # dev server on :8001 (Decision 014 — port 8000 has an unkillable phantom listener). NOTE: on Windows, `taskkill /PID <n> /F` alone does NOT kill uvicorn --reload's orphaned multiprocessing worker child — it survives holding the socket, looking exactly like an unkillable phantom. Find it via `Get-CimInstance Win32_Process | Where-Object {$_.CommandLine -match "multiprocessing"}` (its ParentProcessId is the reloader PID you tried to kill) and kill that child PID too, or use `taskkill /PID <n> /F /T` up front (Decision 042).
./.venv/Scripts/python.exe -m database.init_db            # create tables from models (also backend/init_db.py, duplicate); must be run as a module — `python database/init_db.py` fails with ModuleNotFoundError since backend/ never lands on sys.path that way
./.venv/Scripts/python.exe create_admin.py                 # create admin@dmcos.com / Admin@2026
./.venv/Scripts/python.exe check_db.py                     # inspect dmc.db tables/columns via sqlite3
```
Dependencies are pinned in `backend/requirements.txt` — install with `./.venv/Scripts/pip.exe install -r requirements.txt` (or into a fresh venv). The `.venv` is committed to the repo; if it's ever recreated, install from this file rather than guessing packages.

Frontend (React + TypeScript + Vite, from `frontend/`):
```
npm run dev       # vite dev server, expects backend at http://127.0.0.1:8001
npm run build      # tsc -b && vite build
npm run lint       # oxlint
```
No test suite exists in either backend or frontend.

## Known issues (tracked, not yet fixed)

- **"Today" in the browser must be the LOCAL calendar date, never `toISOString().slice(0, 10)`.** That expression is the date in UTC. `Reservations.tsx`'s `todayStr()` used it, so east of Greenwich the screen believed it was still yesterday for the first hours of every day (00:00–05:00 at UTC+5): the admin queue asked for "created yesterday", the server's unowned-booking carry-forward (Decision 164, which only fires for a range containing the *server's* today) did not, and the default view came up **empty every night** — reproduced with a frozen clock, 0 rows at 00:30 against 10 at midday. The cancellation-fee preview and the "arrives in N days" flags were a day off in the same window. Fixed to `toIsoDate(new Date())`. `BookingsSubViews.tsx` had the same defect and was fixed when it was rewritten as the Transfer list (Decision 210). **Limit of the fix:** it matches the server only when browser and server share a timezone; an agent abroad can still differ by a day near midnight, which needs the server to state its date rather than the browser guessing.
- **Flight times are 24-hour TEXT inputs everywhere, never `<input type="time">` (Decision 150).** The native control renders in the **browser's** locale — on a 12-hour machine it demands an AM/PM segment and yields `""` until one is picked, so a typed "09:00" silently saves as empty; and a partially-entered native date/time input is `badInput`, which invalidates the whole enclosing `<form>` and blocks submit with no on-screen message. The columns are `String(5)` holding `08:45`/`14:20`, so text is the closer fit anyway. Use `formatTimeInput`/`isValidTimeValue` (exported from `HotelSearch.tsx`); forms containing date/time inputs should be `noValidate` and validate themselves.
- **FastAPI's `detail` has two shapes — always run it through `formatApiDetail`.** A deliberate `HTTPException` gives a string, but a 422 validation failure gives a **list** of `{loc, msg}` objects; passing either straight to `new Error()` renders `[object Object]` to the user (a real, reported failure). Both `HotelSearch.tsx` and `Reservations.tsx` carry a copy of the helper alongside their own `fetchJson`.
- **Legacy global CSS silently breaks every native radio and checkbox.** `frontend/src/styles/components.css` (imported into the `legacy` cascade layer by `tailwind.css`) applies `width: 100%; padding: 14px 16px; border: 1px solid #d1d5db` to **every** `input` — including `type="radio"` and `type="checkbox"`, which get stretched across their container with the label pushed away from the control. Found live in Decision 150's first version (the flight-mode radios rendered with the dot on the far left and the text on the far right). Tailwind's preflight is deliberately excluded, so nothing resets this. **Two working patterns exist in the codebase:** add explicit size utilities (`h-4 w-4 accent-gold`, as `HotelSearch.tsx`'s transfer-option radio has always done — utilities beat the legacy layer), or avoid the native control entirely and build a selectable card/pill from `<button>` (Decision 150's flight step). A global `input[type="radio"], input[type="checkbox"] { width:auto; padding:0; border:0 }` exception would fix it once for everything, but it would also change how `Login.tsx`'s and `Register.tsx`'s existing checkboxes render — left alone rather than restyling two screens nobody asked about.

- **`AgentDashboard.tsx` (v1) is dead code, not deleted.** Superseded by `AgentDashboard_v2.tsx` (which `router.tsx`'s `/agent-dashboard` route actually renders), imported nowhere in the live app. Carries its own copy of the pre-Decision-134 redirect-loop trap (redirects on a missing token without clearing stale `role`/`user` first) and 2 of its own unused-variable baseline `tsc -b` errors — both harmless since the file never executes, left alone rather than expanding an unrelated task's scope. Delete only in a dedicated cleanup pass, along with the similarly-orphaned `Hero.tsx`/`AgentRegistration.tsx` (confirmed nowhere-imported during Decision 134's investigation).
- **Admin screens are addressable (Decision 201).** The section and the Bookings view live in the URL as query parameters on `/admin-panel` (`?section=invoices`, `?section=transfer-list&view=departures`); no parameters means Bookings, the list. `view` belongs to the Transfer list alone (Decision 210); an old `?view=arrivals` opens Bookings and is corrected. Refresh, Back and Forward work; an invalid value falls back to the default screen and the address is corrected. `adminLocation.ts` is the single definition of the address format. The Bookings screen's queue, filters, sort and page are kept across a refresh in `sessionStorage`, not the URL (Decision 207). **Still not kept:** the open booking, other admin pages' filters (Transfer list included), and the top-bar page tabs after a refresh.
