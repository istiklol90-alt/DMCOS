# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Engine Development Rule (non-negotiable)

Each of the 22 Core Engines must go through its FULL lifecycle (TASK-000 through TASK-006 LOCK) before work begins on the next Engine. No parallel Engine work. No starting a new Engine's TASK-001 while a previous Engine is still in progress. This was proven with Authentication Engine (fully migrated, tested, documented, and LOCKED before any other Engine was touched) and must be repeated for every subsequent Engine, in this exact order, unless explicitly told otherwise by the project owner.

Before starting any Engine that depends on another Engine's data (e.g. Booking Engine depends on Contract Engine for pricing), an **Interface Contract** document must exist first, defining exactly what functions/data one Engine provides to the other. Interface Contracts live in `docs/interface-contracts/`, named `<engine-a>-<engine-b>.md` (e.g. `contract-hotel-booking.md` for the Contract → Hotel → Booking data flow). This directory doesn't exist yet — create it when the first cross-Engine dependency actually needs one, rather than speculatively.

## Project

DMC Travel OS — a Destination Management System (DMC/tour-operator ERP: agents, hotels, contracts, rates, bookings, payments, finance, AI automation). Currently in early MVP stage: only authentication and agent-registration/approval are implemented end-to-end; most business modules listed in the design docs (hotels, contracts, rates, bookings, finance, transfers, charter, AI) do not exist in code yet.

The numbered root-level docs are the project's spec and are treated as the source of truth for business rules, not just background reading:

- `00_MASTER_RULES.md` — golden rules. Notably: never change business logic without owner confirmation, don't remove existing features without reason, AI must follow `02_Logic_Rules.md` / `03_Domain_Model.md` / `04_Data_Dictionary` and must not invent its own business rules.
- `01_Modules_List.md` — full business module catalog (most are unbuilt).
- `02_Logic_Rules.md` — detailed workflow/status rules (agent registration, contracts, rates, bookings, etc.).
- `03_Domain_Model.md` — canonical entity/field definitions.
- `04_Data_Dictionary` (no extension, it's a text file, not a folder) — DB field dictionary. Note it specifies UUID primary keys + `tenant_id` on every table; actual code currently uses integer PKs and no multi-tenancy (see Reality vs. docs below).
- `05_Architecture.md` — target architecture (Postgres, Redis, Celery, S3, multi-tenant). Aspirational; current implementation is much simpler (see below).
- `06_API_Rules.md`, `07_UI_UX_Rules.md`, `08_Coding_Standards.md` — API/UI/coding conventions to follow for new work.
- `09_Project_Roadmap.md` — phase plan (currently in Phase 2 / MVP).
- `11_Decisions.md`, `12_REVIEW.md` — decision and review logs; templates are mostly still empty.

**Reality vs. docs gap:** the docs describe the long-term target (PostgreSQL, UUIDs, multi-tenant, Celery/Redis, S3). The actual backend today is a single-tenant FastAPI app on SQLite with integer auto-increment PKs and no queue/cache/storage layer. When implementing new features, follow the doc's business rules and API/module shape, but don't assume the infra described in `05_Architecture.md` already exists — check the code first.

## Commands

Backend (FastAPI, from `backend/`, using the committed `.venv`):
```
./.venv/Scripts/python.exe -m uvicorn main:app --reload --port 8001   # dev server on :8001 (Decision 014 — port 8000 has an unkillable phantom listener). NOTE: on Windows, `taskkill /PID <n> /F` alone does NOT kill uvicorn --reload's orphaned multiprocessing worker child — it survives holding the socket, looking exactly like an unkillable phantom. Find it via `Get-CimInstance Win32_Process | Where-Object {$_.CommandLine -match "multiprocessing"}` (its ParentProcessId is the reloader PID you tried to kill) and kill that child PID too, or use `taskkill /PID <n> /F /T` up front (Decision 042).
./.venv/Scripts/python.exe -m database.init_db            # create tables from models (also backend/init_db.py, duplicate); must be run as a module — `python database/init_db.py` fails with ModuleNotFoundError since backend/ never lands on sys.path that way
./.venv/Scripts/python.exe create_admin.py                 # create admin@dmcos.com / Admin@2026
./.venv/Scripts/python.exe check_db.py                     # inspect dmc.db tables/columns via sqlite3
```
Dependencies are pinned in `backend/requirements.txt` — install with `./.venv/Scripts/pip.exe install -r requirements.txt` (or into a fresh venv). The `.venv` is committed to the repo; if it's ever recreated, install from this file rather than guessing packages.

Frontend (React + TypeScript + Vite, from `frontend/`):
```
npm run dev       # vite dev server, expects backend at http://127.0.0.1:8001
npm run build      # tsc -b && vite build
npm run lint       # oxlint
```
No test suite exists in either backend or frontend.

- **Booking engine — `app/engines/booking/` — Status: 🔒 LOCKED.** Built, tested, and production-validated (TASK-000 through TASK-006). The first Engine that reaches into two other Engines simultaneously — `service.py` imports both `app.engines.hotel.service` and `app.engines.contract.service` directly, per `docs/interface-contracts/contract-hotel-booking.md`. `models.py` defines 2 tables: `bookings` (grounded in `03_Domain_Model.md` #37/`02_Logic_Rules.md` #45-51) and `guests` (`03_Domain_Model.md` #38). `Booking.contract_id`/`rate_id`/`meal_plan_id`/`currency`/`total_amount` are all `NOT NULL` and resolved **server-side only** — `BookingCreate` never accepts them from the caller, so a client can never set its own price. `total_amount`/`currency` are a frozen snapshot taken once at booking time, never recomputed even if the contract's rates/promotions change afterward. `Guest.is_lead_guest` is a boolean flag standing in for "Lead Guest" (`02_Logic_Rules.md` #50) rather than a nullable FK on `Booking`. `schemas.py`'s `BookingUpdate.status` deliberately excludes `"Cancelled"` at the type level — cancellation only goes through the dedicated `BookingCancelRequest` (`02_Logic_Rules.md` #49: "every cancellation must have reason").
  - **Core business flow — reserve-at-creation, not reserve-at-confirmation:** `service.create_booking` validates the hotel/room/agent, resolves the hotel's currently-**active** contract (`02_Logic_Rules.md` #45: "Booking cannot exist without an active contract"), calls Contract Engine's `check_allotment`, prices the stay via `get_room_price`, calls Contract Engine's `reserve_allotment` (added specifically for this — see Decision 011), and only then inserts the `Booking` row with `status="Pending"` — **not** the model's column default `"Draft"`. `Booking.status`'s `"Draft"` default is effectively unreachable through `create_booking`: since `contract_id`/`rate_id`/pricing must all be resolved before insert (`NOT NULL`), and resolving them already means `check_allotment`/`reserve_allotment` have run, by the time a row can exist it's already a live, inventory-holding request — matching `02_Logic_Rules.md` #46's workflow, where "Agent submits booking request" and "Booking is created" are the same step, not two.
  - **Changed (Decision 104) — cancellation is now two-stage, not atomic:** `service.cancel_booking` (stage 1, same endpoint/function name, changed behavior) computes and **freezes** `cancellation_fee` from Contract Engine's `get_cancellation_policy` tier list (interpretation unchanged: among tiers where the actual notice is less than that tier's `days_before_arrival` threshold, the tier with the *smallest* threshold — the strictest one actually triggered — wins; no fee if no tier's threshold is breached), records status=`"Cancellation Requested"`/reason/timestamp/fee/who atomically via `repository.request_cancellation` — but does **not** call `release_allotment` anymore. New `service.confirm_cancellation` (stage 2, `POST /bookings/{id}/confirm-cancellation`, `_require_admin`-gated) requires `cancellation_confirmation_number` and is the only thing that finalizes `status="Cancelled"` and actually releases the allotment; 3 new nullable columns (`cancellation_confirmation_number`/`cancellation_confirmed_at`/`cancellation_confirmed_by`) capture this stage, additive to the existing stage-1 fields which stage 2 never touches. `service.update_booking_status` still calls `release_allotment` when transitioning into `"Rejected"` — a hotel-declined booking releases its held room the same as before, unaffected by this change.

This is a narrow rule scoped specifically to the allotment-release boundary, **not** a full invented status transition graph; `"Completed"` is deliberately not terminal here since checkout doesn't release anything. `"Cancellation Requested"` (Decision 104) is deliberately **not** added to this terminal set (it must still reach `"Cancelled"`) — instead, `update_booking_status`'s generic path is separately blocked from moving a booking out of `"Cancellation Requested"` at all, and `change_booking_dates` (a different code path with its own status check, never routed through `update_booking_status`) got the identical explicit guard added, closing a real adjacent gap found while implementing this: without it, dates could still be changed on a booking mid-cancellation, leaving the frozen `cancellation_fee` referring to stale dates.

## Frontend architecture

- Entry (`main.tsx`) mounts `router.tsx` (`react-router-dom`), which routes `/`, `/register`, `/login`, `/dashboard`, `/admin-panel`, `/agent-dashboard` to page components — but `App.tsx` (rendered at `/`) *also* implements its own internal page switcher via `useState<Page>` and renders `Home`/`Register`/`Login`/`AdminPanel`/`AgentDashboard_v2`/`ManagerDashboard` conditionally instead of delegating to the router's child routes. In practice nearly all in-app navigation happens through `App.tsx`'s local state (and `localStorage.getItem("role")` on mount), not through the router paths — the router-defined child routes are largely dead paths. Be aware of this split when adding a new page/screen: decide which mechanism it should join rather than assuming the router config is authoritative. See "Known issues" below for the concrete failure modes this causes.
- `config.ts` hardcodes `API_URL = "http://127.0.0.1:8001"` (Decision 014 — port 8000 is avoided due to an unkillable phantom listener; see Decision 042 for a Windows `taskkill`/orphaned-reload-worker gotcha that can make 8001 look phantom-blocked too when it isn't).
- `pages/` — one component per screen (Home, Register/AgentRegistration, Login, ChangePassword, Dashboard, AdminPanel, AgentDashboard, AgentDashboard_v2, ManagerDashboard, CounteragentDashboard). `AgentDashboard.tsx` (v1) is no longer rendered anywhere — `App.tsx` renders `AgentDashboard_v2.tsx` for the agent role instead — but v1 hasn't been deleted.
- **`Reservations.tsx`/`AdminBookingFinance.tsx` split (Decision 107).** `Reservations.tsx` exports the shared, financially-neutral `BookingsList` (guest/flight/confirmation-number editing, date changes, cancellation request+confirm, document downloads, AI flags, correspondence read-display) — imported directly by `AgentDashboard_v2.tsx`. `AdminBookingFinance.tsx` (new) contains everything financial (invoice creation/management, Net/Sale/Profit, price breakdown, LPO compose/send, review-flag/urgent-invoice badges), composed into the base via an optional `adminExtensions` prop (9 named render-prop slots, see `Reservations.tsx`'s exported `AdminBookingExtensions` interface) rather than permission-gated inline rendering — `AgentDashboard_v2.tsx` has zero reference to `AdminBookingFinance.tsx` anywhere in its source, so financial content is structurally unreachable from the agent code path, not merely hidden. `AdminPanel.tsx` imports `AdminBookingsList` (the wrapper `AdminBookingFinance.tsx` exports, hardcoding full admin permissions) instead of the base directly. `Permissions.canManageInvoices` no longer exists anywhere in the codebase — replaced by `canConfirmWithHotel` (gates `ConfirmationNumberEdit`/`CancellationConfirmationEdit`, which stay in the base for "hotel-confirmation authority" reasons, not money-secrecy) plus the extension mechanism itself. Prompted directly by two real production leaks this same session (Decisions 102/106) that were both render-gating omissions in the previously fully-shared file.
- **`BookingsSubViews.tsx` (Decision 113).** Admin-only "Bookings" nav dropdown (`AdminNav.tsx`'s `NAV_STRUCTURE`, same group/children shape as "Contracts"/"Finance") with three specialized read-only views — Transfers, Arrival, Departure — over the same booking data `BookingsList` fetches, no new backend endpoints. One shared `BookingsSubView` component (`mode` prop) with three thin named exports, not three files — not built via `BookingsList`'s `adminExtensions` (that only appends trailing columns; these views need a different base column set entirely). Transfer-type-to-name resolution bulk-fetches the pre-existing `GET /contracts/{id}/transfer-options` per unique `contract_id`. Guest names have a real, documented, accepted limitation: no bulk guest endpoint exists (only `GET /bookings/{id}/guests`, per-booking), so lead-guest names are fetched one call per row, scoped only to the currently-filtered/visible rows (default filter is "This week," keeping the real call count small) — flagged explicitly in code, not silently assumed to scale; a real bulk endpoint should be added only if an unfiltered "every arrival ever" view is ever actually needed.
- `components/` grouped by feature area (`dashboard/`, `counteragents/`, `layout/`, `ui/`).
- Role handling is string-based and inconsistently cased across the stack (backend stores/returns roles like `"Admin"`/`"agent"`; frontend checks both `"Admin"`/`"admin"` etc.) — check exact casing when touching role logic instead of assuming one convention.
- **Language split (Decision 109).** The admin panel (`AdminPanel.tsx` and every file it renders — `AdminNav.tsx`, `financeShared.tsx`, `Invoices.tsx`, `Balance.tsx`, `Cashback.tsx`, `Counteragents.tsx`, `Contracts.tsx`, `ContractsAI.tsx`, `AdminBookingFinance.tsx`, `PriceCalculator.tsx`) is **English-only, permanently** — a one-way text replacement with no i18n library, since there's no language-switching need on the admin side. The agent panel (`Reservations.tsx`, `HotelSearch.tsx`, `AgentDashboard_v2.tsx`) has **real bilingual RU/EN i18n** via `react-i18next`: `frontend/src/i18n/i18n.ts` is the singleton (imported once, side-effect only, in `main.tsx`), translation catalogs live in `frontend/src/i18n/locales/{ru,en}/{common,reservations,hotelSearch,agentDashboard}.json` (one namespace per source file, keys nested by in-file component name). Default language is `"ru"`; a RU/EN pill toggle lives in `Header.tsx` (`i18n.changeLanguage(...)`), persisted to `localStorage["lang"]` (same flat unprefixed-key convention as `token`/`role`/`user`) automatically via an `i18n.on("languageChanged", ...)` listener in `i18n.ts` — never written directly by the toggle itself. `DateRangePicker` (defined in `HotelSearch.tsx`, consumed by `HotelSearch.tsx`/`Reservations.tsx`/admin's `PriceCalculator.tsx`) is the one cross-boundary component: it takes an optional `forceLang?: "en" | "ru"` prop, omitted by the two agent-facing callers (follows ambient `i18n.language`) and set to `"en"` by `PriceCalculator.tsx` (deterministic English via `i18n.getFixedT`, regardless of whatever language an agent elsewhere has toggled).   - **Fixed (Decision 110):** `AdminBookingFinance.tsx` (admin-only) renders `Reservations.tsx`'s shared, real-i18next `BookingsList`/`BookingDetail`, and `AdminPanel.tsx` never renders `Header.tsx` (no reachable RU/EN toggle) — so that embedded subtree was permanently stuck on the ambient global instance's default `"ru"`. Deliberately not done via `i18n.changeLanguage("en")` on the shared singleton, since that would persist through `i18n.ts`'s `languageChanged` listener into the same `localStorage["lang"]` key an agent's own session relies on. Also fixed: both `Reservations.tsx`/`HotelSearch.tsx`'s module-scope `fetchJson` helpers called `i18n.t(...)` on the global singleton directly for their generic HTTP-error fallback string (a plain function has no React context to read, so it bypassed `I18nextProvider` regardless of render location) — made language-neutral (hardcoded English) instead of translated, since every real backend error path already returns `{"detail": "..."}` which overwrites this fallback anyway. **All new Admin Panel code/text must be written in English from the start going forward** — confirmed directly by the project owner.

## Known issues (tracked, not yet fixed)

- **Router/`App.tsx` page-switching mismatch breaks direct-URL navigation and creates a redirect-loop trap.** `App.tsx` never renders `<Outlet/>`, so none of `router.tsx`'s nested child routes actually mount when visited directly by URL — the address bar changes but the visible content is always whatever `App`'s own `page` state resolves to (defaults to `"home"` on a fresh load, or gets set from `localStorage.getItem("role")` in `App`'s mount effect). Confirmed with Playwright: visiting `/agent-dashboard` directly with no session at all just silently renders Home instead of redirecting anywhere.
  - Related trap: a page that guards itself the way `AgentDashboard.tsx`/`AgentDashboard_v2.tsx` do (check `token` in `localStorage`, `window.location.href = "/login"` if missing) will loop forever if it redirects without also clearing the stale `role`/`user` keys — because on the next full load, `App`'s mount effect reads that leftover `role`, routes straight back to the same guarded page, which redirects again. `AgentDashboard_v2.tsx` calls `localStorage.clear()` before redirecting to avoid this; `AgentDashboard.tsx` (v1, unused but still present) does not have this fix and would still loop under the same conditions.
  - Proper fix is its own task, not a drive-by change — it touches how every page in the app is reached. Likely needs either: wire `App.tsx` to actually delegate to the router (add `<Outlet/>`, drop the internal `page` state), or remove `router.tsx`'s dead nested routes and rely solely on `App`'s state machine.
