# Interface Contract: Hotel ↔ Contract ↔ Booking

## Hotel Engine provides (already built, LOCKED)

All functions live in `app.engines.hotel.service` and take a SQLAlchemy `Session` as their first argument (`db: Session`), verified against the real code as of Hotel Engine LOCK:

- `get_hotel(db, hotel_id)` — returns the `Hotel` row, or raises `ValueError` if it doesn't exist.
- `list_room_types(db, hotel_id)` — returns all `RoomType` rows for one hotel.
- `get_room_type(db, room_type_id)` — returns one `RoomType`, includes `max_occupancy`; raises `ValueError` if not found.
- `list_room_occupancy_options(db, room_type_id, active_only=False)` — valid adults/children/infants combinations for a room type (infants excluded from `max_occupancy`).
- `list_room_availability(db, room_type_id, start_date=None, end_date=None)` — day-by-day Free Sale / On Request / Closed status (`"free_sale"` / `"on_request"` / `"closed"`) for a room type. **Not** an allotment count — that's Contract Engine's responsibility.
- `validate_capacity(db, room_type_id, adults, children)` → `None`. **Added post-LOCK per Decision 015** (purely additive — no existing signature changed), mirroring Decision 011's shape. Raises `ValueError` if `adults + children` exceeds the room type's `max_occupancy` — a thin wrapper around the already-existing `validate_occupancy_within_capacity` validator, exposed through Hotel Engine's service boundary so Contract Engine's `get_room_price` doesn't need to reach into `hotel.validators` directly. Infants excluded, same rule as `list_room_occupancy_options` above.

All of the above raise plain `ValueError` on failure (not-found and invalid-input alike — a known simplification, see `11_Decisions.md` and `CLAUDE.md`'s Hotel Engine section), not a dedicated exception type.

## Contract Engine provides (already built, LOCKED)

All functions live in `app.engines.contract.service` and take `db: Session` as their first argument, matching Hotel Engine's own convention, verified against the real code as of Contract Engine LOCK:

- `get_active_contract(db, hotel_id, check_in_date=None)` → `Optional[Contract]`. **As of Decision 018**, returns the contract usable for a given check-in date at this hotel: `contract_status == "Active"` AND `start_date <= check_in_date <= end_date`, both required. `check_in_date` defaults to today only for backward compatibility with a caller that omits it — every real caller (Booking Engine's `create_booking`, HotelSearch.tsx via the API) passes the actual check-in date being searched/booked, so a future stay against a not-yet-started-by-today contract still resolves correctly. If more than one contract qualifies, returns the first by id — real multi-contract priority (market/travel-date matching) isn't resolvable with this signature; revisit if that scenario comes up.
- `get_room_price(db, contract_id, room_type_id, check_in, check_out, meal_plan, adults, children, infants=0)` → `dict` with keys: `contract_id`, `room_type_id`, `rate_id`, `season_id`, `meal_plan_id`, `used_meal_plan_supplement`, `currency`, `nights`, `occupancy` (`{adults, children, infants}`), `base_total`, `supplements_total`, `price_before_promotions`, `applied_promotions` (list of promotion ids), `final_total`. `adults`/`children`/`infants` match Hotel Engine's occupancy shape exactly (infants excluded from any capacity check). Known simplifications: only the season covering `check_in` is used for the whole stay (no multi-season proration), and `adults`/`children`/`infants` are mapped onto the contract's `ContractAgeCategory` rows by name-keyword matching (`"adult"`/`"infant"`, first remaining category treated as "children") — a contract with more than one child-like category (e.g. both "Teen" and "Child") can't be fully disambiguated by this 3-bucket signature. **As of Decision 015**, this now calls Hotel Engine's `validate_capacity` before pricing anything — raises `ValueError` if `adults + children` exceeds the room type's `max_occupancy`, closing a gap where occupancy was never checked anywhere in the pricing or booking path.
- `check_allotment(db, contract_id, room_type_id, check_in, check_out)` → `bool`. True only if every night in range has an allotment row with `available_rooms > 0` AND no active Stop Sale blocks that night. **Known limitation: checks "at least one room available," not a specific requested quantity — there is no room-count parameter in this signature.** Most bookings are single-room; multi-room group bookings already carry separate negotiated contract terms in practice. Revisit only if Booking Engine actually needs a multi-room check.
- `get_cancellation_policy(db, contract_id, check_in)` → `list[CancellationPolicy]`. Returns every applicable tier (contract-wide tiers plus any whose date range contains `check_in`) — **does not resolve to a single answer.** Multiple tiers are expected (e.g. 30 days=10%, 14 days=50%, 7 days=100%); Booking Engine must pick the correct tier itself based on the actual number of days before arrival at the moment of cancellation, which this function has no way to know in advance.
- `get_meal_plans(db, contract_id, room_type_id)` → `list[ContractMealPlan]`. **As of Decision 021**, returns meal plans priceable for this room type either via a direct `Rate` row, or via an active `meal_plan_supplement` `RateSupplement` on one of this room type's rates (the same fallback `get_room_price` already supports) — not every meal plan defined anywhere on the contract.
- `get_child_policy(db, contract_id, room_type_id)` → `list[dict]`, each shaped `{category_name, min_age, max_age, prices: [{rate_id, amount, calculation_basis}, ...]}`. **Not a stored entity or a Pydantic schema** — an ad-hoc computed view derived from `ContractAgeCategory` + `RateSupplement` rows at call time.
- `get_transfer_options(db, contract_id)` → `list[ContractTransferOption]`. **Added post-LOCK per Decision 022** (purely additive). Only Active transfer options for this contract — the set an agent can actually select. `ContractTransferOption.transfer_type` is a free-form string (e.g. `"seaplane"`, `"domestic_comfort"`), not an enum, so a hotel-specific transfer kind is new data, never a schema change. Whether a transfer selection is required at all lives on `Contract.transfer_required` (a single contract-level flag), not on the individual option — `transfer_required=true` means "the agent must pick exactly one of these options," not "every option is individually mandatory."
- `get_transfer_price(db, contract_id, transfer_type, check_in, check_out, adults, children, infants=0)` → `dict` with keys: `contract_id`, `transfer_type`, `transfer_name`, `currency`, `occupancy` (`{adults, children, infants}`), `price_adult`, `price_child`, `price_infant`, `total`. `total = price_adult * adults + price_child * children + (price_infant or 0) * infants` — **not multiplied by nights**, since a transfer is a one-time round-trip charge, unlike `RateSupplement`'s `per_person_per_night` pattern. `currency` comes from the contract itself; `ContractTransferOption` has no currency column of its own. **As of Decision 026**, `check_in`/`check_out` are required parameters (added post-Decision-022, which didn't need dates at all) so a `SpecialOfferTransferDiscount`'s `min_nights` and period-matching can be evaluated — keyed by `check_in` (arrival date) only, never `check_out`, per the same check_in-for-the-whole-stay simplification `get_room_price` already uses for seasons. Raises `ValueError` if the contract doesn't exist or has no Active option with that `transfer_type`.
- `get_room_price` (see above) **as of Decision 026** also applies up to three `SpecialOffer` mechanisms before the existing `Promotion` step: a room-type-and-period percentage discount on `base_total` (optionally also `extra_person`), a percentage discount on the `meal_plan_supplement` contribution specifically, and a waiver of `age_category_price` for up to N qualifying children conditional on a minimum adult count. All three are computed as reductions to already-isolated components (never as a blanket discount on the whole total), so they compose correctly with each other and with `Promotion`'s own sequential-discount step, which still runs on top of whatever `price_before_promotions` these produce.
- `reserve_allotment(db, contract_id, room_type_id, check_in, check_out)` → `None`. **Added post-LOCK per Decision 011** (purely additive — no existing signature changed) once Booking Engine's TASK-002 found there was no way to actually decrement inventory. Increments `sold_rooms` by 1 for every night in range. Validates every night has capacity (active allotment row, `available_rooms > 0`, no active Stop Sale) *before* writing anything, so a failure partway through a multi-night stay never leaves some nights incremented and others not. Raises `ValueError` if any single night fails.
- `release_allotment(db, contract_id, room_type_id, check_in, check_out)` → `None`. **Added post-LOCK per Decision 011**, alongside `reserve_allotment`. Decrements `sold_rooms` by 1 for every night in range (cancellation). Unlike `reserve_allotment`, never raises on a missing or stop-sold night — releasing inventory isn't blocked by a Stop Sale, and a missing allotment row is simply skipped. `sold_rooms` is floored at 0 to guard against double-release.

All of the above raise plain `ValueError` on failure (not-found and invalid-input alike, same known simplification as Hotel Engine — see `11_Decisions.md` and `CLAUDE.md`'s Contract Engine section).

## Rules

1. Contract Engine references Hotel Engine's `hotel_id`/`room_type_id` — never duplicates hotel/room data.
2. Contract Engine owns all pricing/seasonal/discount/cancellation logic — Hotel Engine has none of this.
3. Booking Engine queries Contract Engine for price at time of booking — never caches/stores its own copy of the *live* price (a booking's own `total_amount` is a frozen snapshot taken once at booking time, which is different from caching a reusable price). Booking Engine calls `reserve_allotment`/`release_allotment` to mutate inventory — it never writes to `Allotment` rows directly.
4. Currency comes from the Contract, tied to the destination (per project convention: each destination has its own currency).
