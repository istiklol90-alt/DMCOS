# Interface Contract: Pricing ↔ Booking

## Pricing Engine provides (Decision 069, extended by Decision 071)

All functions live in `app.engines.pricing.service` and take `db: Session` as their first argument, matching every other Engine's own convention.

- `apply_agent_pricing(db, agent_id, contract_id, room_net_total, nights, room_type_id, meal_plan_id, check_in)` → `dict` with keys: `room_net_total`, `is_exclusive`, `contract_discount_percent`, `exclusive_discount_amount`, `markup_amount_per_night`, `markup_amount`, `agent_room_total`. Computation order (owner-confirmed): the exclusive discount only applies when **both** conditions hold — `agent_id` is in `ExclusiveAgent` **and** `find_contract_exclusive_discount(db, contract_id, room_type_id, meal_plan_id, check_in)` finds a matching `ContractExclusiveDiscount` row (no match = no exclusive arrangement for this exact booking, regardless of the agent's tier). When both hold, `room_net_total` is reduced by the matched row's `discount_percent`% first (computed on the tactical-offer-already-discounted net); the global `standard_markup_amount_per_night * nights` is then added on top of that (possibly discounted) net to produce `agent_room_total`. Any other combination (Standard agent, or Exclusive agent with no matching row) skips the discount step entirely (`exclusive_discount_amount = 0`).
- `find_contract_exclusive_discount(db, contract_id, room_type_id, meal_plan_id, check_in)` → `ContractExclusiveDiscount | None` (Decision 071). A contract can have **multiple** `ContractExclusiveDiscount` rows at different specificity/date-window combinations — `room_type_id`/`meal_plan_id` NULL means "applies to all" (same wildcard convention as Contract Engine's own `SpecialOfferRoomDiscount.room_type_id`), `start_date`/`end_date` NULL means "always active" on that side. A row is a match only if its non-NULL fields all match exactly and `check_in` falls inside its date window (if any). Among matches, **most-specific-wins**: the row matching the most of `{room_type_id, meal_plan_id}` is selected; ties prefer a row with an explicit date window over an always-active one. Same tier-selection discipline as Decisions 051/053.
- `apply_agent_pricing` does **not** itself validate that `agent_id` refers to a real `User` — it trusts the caller already did this (Booking Engine's `create_booking` already calls `_require_agent` before any pricing happens). An unrecognized `agent_id` simply resolves to "not exclusive," never an error. It also does not validate `contract_id` exists — an unrecognized `contract_id` simply resolves to "no discount available," never an error, since Booking Engine has already resolved a real `contract.id` by the time this is called.
- `PricingSettings` (markup only, no discount percent — that lives on `ContractExclusiveDiscount` rows) is get-or-created on first read (`get_pricing_settings`) — this function can never raise for "settings missing."
- Only `room_net_total` is touched. Transfer price and mandatory tax are the caller's responsibility and are never modified by Pricing Engine.

## Rules

1. Pricing Engine never imports or calls Contract Engine's `service.py` directly — it operates purely on plain numbers/ids (`room_net_total`, `nights`, `contract_id`, `room_type_id`, `meal_plan_id`, `check_in`) that the caller has already resolved via Contract Engine. This is a deliberately looser coupling than Booking Engine's own direct imports of Hotel/Contract Engine's `service.py` — Pricing Engine has zero code dependency on either engine's function signatures.
2. Booking Engine (`create_booking`) calls `apply_agent_pricing` after `contract_service.get_room_price` and before constructing the `Booking` row, using the returned `agent_room_total` as `total_amount` (replacing the previous `price["final_total"]`), and persists `exclusive_discount_amount`/`markup_amount` in `Booking`'s own itemized columns (`agent_exclusive_discount_amount`/`agent_markup_amount`) — same "separate column so Finance Engine can itemize later" precedent as `transfer_total`/`mandatory_tax_total` (Decisions 022/033).
3. Transfer (`transfer_total`) and mandatory tax (`mandatory_tax_total`) are never modified by Pricing Engine — they remain exactly as Contract Engine computed them, unchanged from today.
4. `ExclusiveAgent.user_id`/`assigned_by` and `ContractExclusiveDiscount.contract_id`/`room_type_id`/`meal_plan_id`/`created_by` reference Authentication/Hotel/Contract Engine's real ids as plain Integers, never a SQL `ForeignKey` — same cross-engine decoupling convention as `agent_id` everywhere else in this project.
5. Absence of an `ExclusiveAgent` row means Standard — new agent registrations require zero code changes to default to Standard; only Exclusive membership is ever explicitly stored. A contract with zero `ContractExclusiveDiscount` rows has no exclusive-agent arrangement at all — most contracts will have none, by design, not as a gap to fill in later.
6. `ContractExclusiveDiscount` is managed through the existing Contracts admin view (`frontend/src/pages/Contracts.tsx`), as a list of rows per contract, not a separate admin surface — keeps all of a contract's terms (rates, seasons, transfer, and now the exclusive discount rows) in one place.
